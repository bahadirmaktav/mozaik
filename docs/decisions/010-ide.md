# 010 — IDE module (V0.7)

Specification: local `.plans/tessera-v0.7-plan.md`. A first working IDE to evaluate the
layout and feature set; not a VS Code copy. Build and run came later with CMake
([011](011-cmake.md)), debugging with V0.8 ([012](012-debugging.md)) and tests with the
Testing view ([013](013-testing.md)).

## Panels, not a second workspace

The IDE is five built-in plugins in the ordinary workspace. There is no IDE window, no
inner tab bar for files and no inner split system. The launcher lists only **IDE** (the project
sidebar); picking it opens the rest with it, so the IDE is added as a whole:

| Plugin                                | Instance                                    | View                                                                                                          |
| ------------------------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `ide` (IDE Project)                   | One project root (single root per panel)    | Activity bar: Explorer (files, Outline) / Search / Source Control / Run and Debug / Testing / TODOs / Results |
| `code` (Code Editor)                  | A text document (the shared document store) | CodeMirror with IDE extensions and a thin bar (path, language server state)                                   |
| `ide-panel` (Panel)                   | A project's bottom panel (`panels.ts`)      | Problems / Terminal views                                                                                     |
| `ide-status` (Status Bar)             | A project's status bar (`panels.ts`)        | Git branch, error/warning counts                                                                              |
| `diff` (Changes, not in the launcher) | A file path                                 | Read-only last commit ↔ current text                                                                          |

Placement uses the existing model (the `open` action has an optional `ratio` and `before`).
Launching the IDE builds, around the sidebar: the status bar under the whole IDE, an empty
Code Editor right of the sidebar (narrow sidebar share) and the bottom panel under that code
editor (30 %). The bottom panel thus spans the code column only, never the sidebar (a review
decision, like VS Code's panel). The first file opened takes the place of the empty editor
while it is untouched; later files become tabs in the last focused code panel; "Open to the
Side" splits it. Problems reopens a missing bottom panel under the code. When the workspace
has no room (minimum sizes), parts without room are left out and Problems says so. Two files
side by side are two Mozaik panels; the same document is never shown twice. The first IDE of
a window opens the folder opened last (`ide-recent.json` in the app config directory, used
only while that folder exists).

**Docked tools** (second V0.7 review): the sidebar, the bottom panel and the status bar have a
`dock` in their plugin definition. A docked tool is always alone in its panel (a tab next to
it becomes a split, a tab dropped on it is refused), has no tab strip, close or maximize
button — its view draws its own bar — and can be **minimized** to that bar: the sidebar to its
40 px activity bar (clicking the shown view's icon minimizes, another icon restores), the
bottom panel to its 30 px bar of views. The model keeps a `collapsed` flag per panel; a
collapsed side of a split along its dock axis gets the bar size and the split keeps its ratio
for restoring. The status bar is `fixed` at its bar size. The sidebar's header shows the view
name (Explorer, Search, Source Control); the project folder's name heads the tree. Closing any
part (Ctrl+W, or Close IDE in the sidebar's ⋯ menu) closes the sidebar, bottom panel and
status bar together; when it is the window's last IDE, its code editors and comparisons close
with it (unsaved files ask). Ctrl+Shift+C (Close Panel) on any part, a code editor included, asks
and then closes the whole IDE. While an IDE is open the code editor area cannot disappear:
closing the last tab of a code panel puts an empty editor in its place, and that empty editor
has no close button.

Since the eleventh review (user request) that empty editor is an **empty code area**: no tab and
no editor, only a hint, as VS Code's empty editor group. The IDE opens with it instead of an
"Untitled" tab; a double click on the free tab bar (or its +) adds a new untitled code file
there, as in the Text Editor, and the area goes; closing the last code tab brings it back. A
new untitled file is an ordinary tab with a close button.

**Bottom panel**: like the sidebar, it switches views in its own bar — Problems (the project's
diagnostics and build problems), Output (CMake), Terminal and, after a CMake Run, Run (see
[decision 011](011-cmake.md)). The status bar under the IDE shows the
Git branch and the error/warning counts (a click shows Problems). Its terminal is an ordinary
Terminal session created the first time the view is shown and started in the project folder
(Rust accepts only an existing absolute directory there; it is never run), kept while the view
is hidden and ended with the panel. An exited shell offers Restart Terminal. The language
server's state is in the code editor bar (its failure details in the tooltip) and Project
Settings, not in a separate status line.

## Editor

The Code Editor is a separate component from the Text Editor (`src/plugins/ide/CodeEditor.tsx`)
with line numbers, folding, bracket matching and closing, auto-indent, multiple selections
(Alt+click, Ctrl+D, Ctrl+Alt+Up/Down, Shift+Alt+drag rectangles), Ctrl+L line selection that
grows by a line, the CodeMirror search/replace panel, go to line,
lint markers and completion. Syntax comes from `@codemirror/language-data` (each language is
a lazy chunk), with an IDE highlight style readable on the dark background. CMake files
(`CMakeLists.txt`, `*.cmake`) use Mozaik's own language (`cmakeLanguage.ts`) instead: commands,
control flow, `${…}` variables, generator expressions, known keywords and bracket comments are
colored, and completion offers CMake's commands, keywords and common variables plus the
targets, variables and functions the file defines. It is offline and in the renderer: a CMake
language server (such as neocmakelsp) would be a second server process, which the product
boundary leaves to clangd alone.

What is shared is deliberate and small: the **document store** (path, text, saved text,
revision, BOM, line endings, conflict), the theme and the native file commands. Therefore the
existing safety applies unchanged to code: explicit save, unsaved marker, close prompt,
recovery snapshots, watcher reload of clean documents and conflict for dirty ones, and one
document per file (opening a file already open in a Text Editor activates that tab).

Keys: CodeMirror's standard keymaps and, at the user's request, F12 / Ctrl+click definition,
Shift+F12 references, F2 rename, Ctrl+L expand line selection, Ctrl+Alt+Up/Down add cursor and
Alt+O switch header/source (clangd's `textDocument/switchSourceHeader`), Ctrl+K Ctrl+C / Ctrl+K
Ctrl+U add/remove line comments (ninth review; as in VS Code, a chord's second key is dropped
when it finishes no chord, and Workspace Settings records chords as two presses), every action also in
the right-click menu (the bar's ⋯ went in the tenth review) and the command palette. CodeMirror's own Ctrl+Alt bindings stay removed because they are
AltGr on many layouts; the arrow bindings are kept because AltGr+arrow types nothing. Ctrl+click
used to add a cursor, which is now Alt+click (rectangles need Shift+Alt). All of these are
rebindable in Workspace Settings (decision 007).

A file shows where it was left, as in VS Code: switching tabs, opening it from the explorer, Go
to File or Switch Header/Source keep its cursor and scroll position, also after its tab was
closed and it is opened again in that window. A jump to a location (definition, result, symbol,
Back) still goes to that location. The places live in the window's memory only, never on disk: a
new window or session starts files at the top, and no layout or file is reopened by them.

## Project explorer

A tree of the project root, folders first, loaded lazily per expanded folder through the
File Manager's listing and watch commands (`.git` hidden). Explorer, Search and Results are
switched from a narrow icon bar on the sidebar's left edge; the explorer has no toolbar
buttons. New file/folder (tree right-click menu), rename (F2),
Trash after confirmation (Delete), and move by dragging onto a folder (refused on a name
conflict, never replaced). The drag uses pointer events, like the File Manager, because the
native file drop handler can swallow HTML5 drags in WebView2. Open documents follow a rename or move. It is not the File Manager:
no permanent delete, sorting or hidden-file setting.

Since the eighteenth review, at the user's request and after VS Code: the project title shows
New File, New Folder, Refresh and Collapse Folders while the section is hovered; rows carry
kind icons drawn in Mozaik after vscode-icons (`fileIcons.tsx`: a colored badge per file kind,
colored well-known folders; nothing loaded); Ctrl+click, Shift+click and Shift+arrows mark
several rows, which Delete, drag and **Ctrl+X/C/V** (`explorer.*` shortcuts) act on. The
clipboard is the File Manager's, so files move between the two. A name in use asks Keep Both,
Replace or Skip (a drag no longer refuses it); a file copied onto itself keeps both. The
dragged item (or "N items") follows the pointer.

Since the twentieth review: the box-shaped badges are gone. **File icon themes**
(`ideIconTheme` preference, Preferences: File Icon Theme in the palette with a live preview
like the color theme, or Settings → IDE → Explorer): Seti (default; VS Code's style, a
colored glyph per file kind without a box and no folder icons), Seti with Folders (colored
folders; a well-known one, such as src, include, tests, build or cmake, carries a badge of
its kind cut out of its lower right, as in the Material icons), Minimal (outlines) and None.
They are drawn in `fileIcons.tsx`, nothing is loaded. New items and renames are typed in the tree's row (`InlineName`, as the
File Manager does) instead of the palette's prompt; rows never select text; a click on the
empty space clears the selection; Ctrl+Z/Ctrl+Y undo and redo file operations
([025](025-file-undo.md)). A gear at the bottom of the activity bar opens Workspace Settings on
its IDE tab.

**Filtering**: the tree shows everything except `.git`; what Git ignores is dimmed. Quick
open and project search honour
`.gitignore` (also outside Git repositories, via the `ignore` crate) and the project's exclude
patterns, and skip `.git`.

## Navigation and search

- **Go to file** (project ⋯ menu): fuzzy ranking of the project's file list (up to 50,000
  files, Rust walk), favouring file names, word starts and runs.
- **Back / Forward**: jumps (definition, results, problems, outline, quick open) record where
  they started; up to 50 places per window. Alt+Left / Alt+Right in the code editor (as in VS
  Code) and Go Back / Go Forward in its menu; the editor bar has no buttons for them (sixth
  review). The place a jump lands on (definition, declaration, implementation, a reference,
  result, problem or symbol) is highlighted for 1.2 s: the word, on a tinted line, fading out
  (static without motion). Debugger frames have their own paused-line highlight instead.
- **Ctrl+D** adds the next match of the selection (the word under the cursor first) to the
  selections, as VS Code's Add Selection to Next Find Match; rebindable as "Add selection to
  next find match".
- **Project search**: text or regular expression (Rust `regex` syntax), match case, whole
  word, within lines; files over 4 MiB, binary or non-UTF-8 files are skipped and counted;
  at most 5,000 matches. Columns are UTF-16, the editor's unit.
- **Replace All** asks first and states what happens: open documents change in their editors
  and stay unsaved (undoable); closed files are rewritten by Rust only if they still have the
  revision seen by the search, with encoding and line endings kept and an atomic replace. A
  changed file is reported and left alone. Open buffers get the replacement computed by the
  same Rust code, so `$1`/`${name}` groups mean the same everywhere.

## Language servers

**Native side** (`src-tauri/src/lsp.rs`): a server is started only by name (`clangd` is the
only one); the program is found on `PATH` or in the usual LLVM locations, or chosen by the
user in a native file dialog and stored in `language-servers.json`. The renderer can never pass
a program path or arguments. Processes are owned by their window, framed with
`Content-Length`, read on their own threads (stderr is drained; its last lines explain an
unexpected exit), and stopped by closing input, then killed after 1.5 s — on panel close,
window close and application exit. No console window on Windows. Arguments are none: clangd
reads the project's `compile_commands.json` and `.clangd` by itself, which keeps existing build
information usable without Mozaik generating it.

**Renderer side** (`src/plugins/ide/lsp.ts`): `@codemirror/lsp-client` (pinned) provides the
JSON-RPC client, document synchronisation, completion, hover and signature help. Mozaik adds:

- A workspace that keeps a file open on the server as long as its **document** is open, not
  just its view, because Mozaik unmounts hidden tabs; reopening per tab switch would reparse
  and drop diagnostics.
- Diagnostics stored per file for Problems and the status bar; shown in the
  editor (lint markers, gutter) when a view attaches.
- Navigation (definition, declaration, implementation, references) that opens Mozaik tabs and
  records history; several results go to the sidebar's Results view.
- **Workspace edits** (rename, quick fixes, server `workspace/applyEdit`): all files are
  validated first; open documents change in their editors (unsaved, undoable); files that are
  not open are listed in a confirmation, then saved with a revision check and atomic replace.
  Creating, renaming or deleting files from an edit is refused. The package's own rename only
  touches open files, so it is not used.
- Formatting (document, selection) applied only if the text did not change meanwhile; **format
  on save** per project, with a 3 s limit after which the file is saved unformatted (a save is
  never blocked by the formatter).
- Outline from `textDocument/documentSymbol`, refreshed 400 ms after typing. There is no
  second parser: without a server the outline says so.
- Server Markdown (hover, completion docs) is reduced to a fixed set of elements without
  attributes, links or images.

**Lifecycle**: the server for a project starts with the first C/C++ file opened in a Code
Editor of that project, not when the IDE opens. A missing or failed server is shown in the
code editor bar (restart and program choice in Project Settings) and is not restarted in a loop; editing continues without
it. Files outside every open project get no server.

Download and version management of language servers is deferred as the plan says; the
settings only find or choose an installed program. Other servers fit by adding a `Server` kind
in Rust and an extension mapping in `paths.ts`.

## Git

`src-tauri/src/git.rs` runs `rev-parse`, `status --porcelain=v2 --branch -z
--ignored=traditional` and `cat-file` (`HEAD:` and index text) with `GIT_OPTIONAL_LOCKS=0`
(no index refresh written), `core.fsmonitor` off (a repository's fsmonitor hook is a program)
and no filters or textconv. The status bar shows the branch (or `detached at …`); the explorer
colours modified, added, renamed, untracked and conflicted files, colours folders after their
most important change (conflict, modified, renamed, deleted, added, untracked) with a dot, and
dims ignored ones (a wholly ignored folder is one entry, so ignored build trees are not listed
file by file).

**Source Control** (fourth V0.7 review, after VS Code) shows the branch and two groups,
**Staged Changes** and **Changes**, from each file's index and working tree side; the
activity bar icon counts the changed files. A row opens its comparison as a tab among the code
editors — a working tree change compares the staged text with the current one (unsaved edits
included), a staged change the last commit with the staged text — and an untracked file opens
itself. Its buttons (on hover or focus) open the file, stage (`git add -A`), unstage (`git
restore --staged`, before the first commit `git rm --cached`) or discard (`git restore
--worktree`, after a confirmation; untracked files go to the Trash through the File
Manager's command); the group titles do the same for every file. Paths are given as
`:(literal)` pathspecs inside the repository. Status refreshes on disk changes in watched
project folders or `.git`, after a project replace, after these actions and on window
focus. Without Git or outside a repository nothing is shown. Commits, push, branches and other
writes stay out of scope.

The comparison is a merge view with the file's syntax colours; removed lines are red on the
left, added lines green on the right. A staged comparison is read only. In a working tree
comparison the right side is the file's document, as in VS Code: it shows unsaved edits, and
editing it (or an arrow between the sides, which puts that change's staged lines back) edits
the document. The first edit opens the file's code tab behind the comparison, so the usual
save (Ctrl+S also works on the comparison), close question, recovery snapshot and conflict
rules apply; without room for that tab the edit is refused. A document read only for a
comparison is dropped with it.

## Palette, Output and terminals (fourth V0.7 review)

- The command palette ([decision 007](007-workspace-shortcuts.md#command-palette)) also finds
  the IDE project's files (Ctrl+P) and the code file's symbols (`@`, Ctrl+Shift+O).
- **Output** lists its channels on the left: **IDE** and **CMake**. IDE messages (a
  definition not found, a failed action) are logged there with the time and shown for a few
  seconds in the IDE status bar (a click opens Output → IDE) instead of a notice over the
  workspace; without an IDE status bar they are still a notice.
- **Terminal** holds several terminals, as in VS Code: + starts another with the default
  shell, ⌄ picks one of the detected shells in the palette, × ends the shown one; with more
  than one, a list beside it switches between them. Restart keeps the shell's kind.
- Code Editor gutter: narrow diagnostics markers, the breakpoint column right beside the line
  numbers (sixth review; it was first, with the markers between it and the numbers), then fold
  chevrons that show while the pointer is over the gutter (always on a folded line). With Ctrl
  held, the word under the pointer is underlined as a link to its definition while a language
  server serves the file. See [decision 012](012-debugging.md) for breakpoints.
- **Sidebar sections** (sixth review), as in VS Code: Explorer (the project's files and
  Outline) and Run and Debug (Variables, Watch, Call Stack, Breakpoints) stack sections that
  fold to their title; open ones share the height and the edge between two of them drags to
  resize (pointer capture, no IPC). A folded section after the open ones stays at the bottom.
  Folded sections and heights (also Source Control's groups and TODOs groups) live in the
  project's state, so they survive switching views; like the rest of a layout they are not
  restored in a new window.
- **TODOs** (sixth review), after VS Code's Todo Tree: an activity bar view listing comments
  tagged TODO, FIXME, BUG, HACK, XXX, NOTE or INFO — the tags are a list in Workspace
  Settings → IDE (`todoTags` in `preferences.json`, at most 50 words of up to 30 characters).
  A tag counts after a comment marker (`//`, `#`, `/*`, `--`, `;`, `<!--`), at the start of a
  block comment line or of a line, followed by a space, `:`, `(`, `[` or the line's end. The
  list is the project search with that pattern (so .gitignore, exclusions and the 4 MiB and
  5,000-match limits apply), saved files only, grouped by file or by tag; a row opens its
  line. It searches when first shown, on Refresh, on new tags and 0.8 s after file changes in
  the project once shown. The code editor colors the tags in place. Not adopted from Todo
  Tree: custom regular expressions, per-tag icons and filters, scanning open unsaved buffers.
- **Status bar** (sixth review): CMake choices and actions carry icons (preset, build preset,
  kit, configure, build), the branch a Git branch icon, and the current code file's line
  ending and encoding moved here from the window's status line.

## Project settings

Stored by Rust per canonical project root in `ide-projects.json` in the app config directory —
never inside the user's repository, and never able to change which programs run: format on
save, tab size, spaces or tabs, exclude patterns (validated as gitignore lines). A damaged file
is reported and left unchanged.

## Not verified

Everything native: the docked layout, minimize and the transparent window on WebView2 and
WebKitGTK, the reopened recent folder, clangd and Git started from the Tauri app on Windows and both Wayland
environments, their shutdown with the window, the folder picker and server program dialog,
watcher refresh, Windows `\\?\` paths through clangd, and IME/clipboard in the code editor
([VALIDATION](../VALIDATION.md#v07-ide-qualification)). The TypeScript client was exercised
against the real clangd in the browser test `ide-clangd.spec.ts`, with Playwright standing in
for Tauri IPC.
